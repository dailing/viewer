# 同一聊天多面板（多分支并排）实现计划

**目标**：同一个 chat 可以在多个 pane 中同时打开，每个 pane 独立选择要看的分支 tab（可相同可不同），独立滚动、独立输入框，都实时更新。

**核心结论**：纯前端改动，**零后端改动**。后端 busy/queue 本来就按 `(chat, branch)` 线键串行化，跨分支并行 dispatch 已支持；阻塞点全部在前端的「pane 身份 = chatId」这一个约定上。

## 现状（已审计）

- pane 身份 = `paneType:instanceId`（`stores/layout.ts` `contentUid` / `openInstance`）；chat 的 `instanceId` **就是 chatId**，`openInstance("chat", chatId)` 遇到同 uid 只聚焦已有 pane，永不新开——这是单 pane 限制的唯一根源。
- `ChatPane.vue` 把 `ctx.instanceId` 同时当两种身份用：
  - **聊天身份**（必须指向同一 chat）：~20 处 RPC `chat_id: ctx.instanceId`、订阅 `chat:{id}:message/block`、`value.chat_id !== ctx.instanceId` 过滤、`chat.value = list.chats.find(item.id === …)`。
  - **视图身份**（必须按 pane 各自独立）：分支 tab 持久化 `viewer.chatBranchTabs.v1` map key（行 262/270）、chatCache key（行 197）、`inputSessionId`（行 38）。
- `plugins/chat/index.ts` dock provider 三处 `layout.isUidOpen(\`chat:${chat.id}\`)` 精确匹配（行 39/42/62）——副本 pane 的 uid 不匹配会导致「开着却被判未开」：dock 条目消失、已读/未读点错乱。

## 方案：view 后缀实例 id（`chatId#view`）

引入复合实例 id：主视图 `chatId`（不变，全兼容），副本视图 `chatId#<随机后缀>`。ChatPane 顶部拆出两个常量：

```ts
const viewKey = ctx.instanceId;               // pane 身份（分支选择/缓存/输入会话按它隔离）
const chatId = viewKey.split("#")[0];         // 聊天身份（RPC/订阅/数据加载按它归属）
```

不开虚拟实例注册表（files 那套 instance-store 模型对这里是过度设计：聊天列表本身就是注册表，副本不需要跨设备恢复——layout 持久化已能让副本 pane 跨刷新存活）。

## 改动清单

### 1. `frontend/src/plugins/chat/ChatPane.vue`（主体）

- 顶部加 `viewKey`/`chatId` 两个常量。
- **聊天身份处换 `chatId`**：全部 RPC payload 的 `chat_id`、订阅 channel `chat:${chatId}:message/block`、`chat_id !==` 过滤比较、`chats.find(item.id === chatId)`。
- **视图身份处保留 `viewKey`**：`inputSessionId`、chatCache key；分支 tab 存储 key 从 `ctx.instanceId`（=chatId）改为 `viewKey`——主视图 key 恰好等于旧 key，老用户的 tab 选择无损保留，副本各自独立。
- 新增 pane chrome action「在新面板打开」（icon `bi-columns-gap` 或 `bi-copy`）：`layout.openInstance("chat", \`${chatId}#${crypto.randomUUID().slice(0, 8)}\`)`。openInstance 对新 uid 走正常分屏/replace 逻辑，无需改动 layout。
- 可选打磨：视图选中单个分支时，pane chrome 标题追加分支名（`聊天名 · 分支名`），便于区分并排的两个 pane。

### 2. `frontend/src/plugins/chat/index.ts`（dock provider）

- 加一个 prefix 感知的打开判定替代三处精确匹配：

```ts
const isChatOpen = (chatId: string): boolean =>
  layout.isUidOpen(`chat:${chatId}`) ||
  layout.panes.some((p) => p.content !== null && contentUid(p.content).startsWith(`chat:${chatId}#`)) ||
  layout.floating.some((p) => contentUid(p.content).startsWith(`chat:${chatId}#`));
```

  用于行 39（markChatRead）、42（dock 过滤）、62（markTurnCompleted 的 open 判定）。语义：任一视图开着即视为聊天开着。
- `chat:_:active`、通知 onclick、`open-chat:<id>` voice 条目仍 `openInstance("chat", chatId)` —— 聚焦主视图，行为不变。

### 3. 不需要动的

- `stores/layout.ts`：`openInstance`/持久化/floating 对任意 instanceId 透明。
- 后端：dispatch 队列按线键并行、RPC 全部按 chat_id 寻址，零改动。
- `voiceDictation.ts`：`voice-fx:chat:${instanceId}` 本来就是 per-pane，语音口述落在具体 pane 上，天然正确。

## 边界与语义（定稿口径）

- 两个 pane 可各自向**不同分支**发消息（服务端跨分支并行已支持）；向同一分支发则共用该线队列（服务端串行化兜底）。
- 未读点：聊天的任一视图开着即标已读（与现状「开着即读」一致）。
- 副本关闭不 pin 即消失，语义与主视图一致（dock 过滤按 prefix 判定）。
- 分支 tab 选择是浏览器本地视图状态（F6 口径），不上服务端。

## 验证

1. `cd frontend && npx vue-tsc --noEmit && npm run build`。
2. 后端无改动，`go build ./... && go test ./...` 确认无意外。
3. E2E 脚本（仿 `/tmp/hermes-verify-*` 惯例）：seed 一个多分支聊天 → 总线层模拟开两个 pane（直接操作 layout store）→ 断言：① 两 pane 各自 load 不同 `branch_ids` 过滤结果；② 分支 tab 选择互不影响且各自持久化；③ dock 条目在只开副本时不消失；④ 任一开着的视图使聊天标已读；⑤ 两 pane 各收 live 帧各自过滤。
4. 手动验收：并排开同一聊天的两个分支，流式输出时两 pane 各自滚动/批刷正常。
