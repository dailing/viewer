# Architecture

This document is the working project map for future agents. Read it before changing code so you can find the right file quickly and understand how the Go kernel, core plugins, frontend, terminal handling, file service, live update flow, and runtime configuration fit together.

Implementation is Go-first: the kernel and all core plugins live under `` (Go), the frontend under `frontend/` (Vue/TS). Python exists only as development tooling under `scripts/` (smoke tests, mocks, migrations); there is no Python product code. The authoritative design documents are `docs/plugin-framework.md` (plugin framework decisions) and `docs/plugin-protocol.md` (wire-level protocol spec); `README.md` is the Go-line build/run manual.

## Purpose

Local Live File Viewer is a private-network workspace for coordinating Codex, Hermes, and OpenCode roles while browsing and editing local files. A Go microkernel (`viewerd`) exposes a WebSocket bus, runs the core plugin set in-process, and serves the built Vue frontend on the same HTTP port. The normal frontend is a single Super Workspace shell with chats, roles, files, Git changes, terminals, Settings, and recursively split panes.

The application assumes a trusted machine and trusted LAN. Terminal, Git, file editing, and Agent processes can modify local files.

## Runtime Flow

1. `viewerd` (single static binary) starts the kernel on loopback `--kernel-host`/`--kernel-port` (defaults `127.0.0.1:8765`) and the gateway on `--host`/`--port` (default `127.0.0.1:18730`). All core plugins are assembled in-process and connect to the kernel over loopback WebSockets through the Go bus SDK — there is no second in-process transport. External plugins connect to the kernel `/ws` directly, and are language-independent.
2. The browser connects to `ws://<gateway>/ws`; the gateway plugin gives each browser connection a dedicated kernel connection whose hello reuses the browser UUID, then relays every later frame byte-for-byte. The same HTTP port serves the embedded frontend (`web/` embeds `web/dist`, built from `frontend`), with `viewerd --static` as the development override.
3. The frontend starts in `frontend/src/main.ts`: creates the Vue app and Pinia, mounts the shell, and lets the in-repo plugin loader register pane plugins (files, chat, voice, plugin-manager). Panes, sidebar, drafts, and scroll positions persist browser-locally; `utils/storage.ts` migrates legacy `.dailing` keys on first access.
4. Chat flow: `ComposerBox.vue` sends the draft through the chat plugin RPC; chat publishes prompt/turn frames over the bus to the selected agent plugin; agent plugins (`viewer.agent-hermes`, `viewer.agent-codex`, `viewer.agent-opencode`) own ACP/App Server stdio subprocesses and publish ordered raw-plus-parsed event frames plus turn-ended events (carrying stop reason and, on prompt failure, the error text); chat persists turns/blocks in `chat.sqlite3` and the frontend incrementally reloads changed runs. A turn whose final stop reason is neither `end_turn` nor `cancelled` is surfaced as a persisted `error` message block (stop reason plus per-attempt error details) rendered as a red single-line row in the timeline. Events are correlated by echoed `turn_id`, never by session-to-turn mapping. User messages may cite any earlier message with an `@<message id>` token (the pane's meta-row cite button on each message box copies the token to the clipboard and appends it to the composer draft, so it pastes into any chat/branch); at dispatch the chat plugin resolves the ids globally — cross-branch and cross-chat — and injects the cited messages' visible text (message rows only, never tool-call/reasoning blocks) as an explicitly labeled section directly before the user query.
5. SIGINT/SIGTERM make the kernel broadcast close 4009 to all connections, then shut plugins down in reverse order and close PTYs, bounded by a 10-second deadline.

## Go Kernel Structure

``

- `internal/protocol/` — five wire-frame shapes, strong hello/envelope validation, UUIDv4 and manifest validation, dotted plugin-id-capable channel/pattern grammar, prefix/`*`/`>` matcher. Payload values are arbitrary JSON.
- `internal/broker/` — serialized subscription table, publish fanout, ordered retained mailbox replacement/replay, atomic subscribe handoff, bounded drop-new outbound queues (corr-tagged WARN on dropped RPC frames), protocol-error delivery, depth guard, no_route fast-fail for subscriber-less RPC requests. `registry.go` owns the retained `plugins:_:list` snapshot and lifecycle events.
- `internal/kernel/` — serves only `/ws`, hello identity, delivery time/origin stamps, oversize-frame rejection, one outbound writer plus ping/pong heartbeat per connection, close 4009 on shutdown. Core assembly and supervisor startup are deliberately outside the kernel.
- `sdk/go/busclient/` — concurrency-safe Go bus SDK shared by in-process and external Go plugins: transport isolation, hello + registry barrier, retained/live handler workers, protocol-error callbacks, inbox RPC/timeout/cancel mapping, exponential reconnect, state callbacks, panic recovery. `assets.go` adds `PushAssets(ctx, client, dir, manifest)`: uploads a built frontend bundle (`frontend.js` entry required) to the gateway, picking one-shot or chunked+append wire mode by size.
- `internal/pluginapi/` — in-process plugin contract, compile-time registry, inspector-first startup, reverse shutdown, loopback kernel-WS wiring, startup deadlines, plugin-level panic isolation.
- `cmd/viewerd/main.go` — assembled single binary: kernel + all core plugins + embedded frontend. Flags: `--host`, `--port`, `--kernel-host`, `--kernel-port`, `--data-dir`, `--static`, `--plugins`. Standalone forms: `cmd/viewer-kernel`, `cmd/viewer-gateway`, `cmd/viewer-terminal`, `cmd/viewer-supervisor`, `cmd/viewer-inspector`, `cmd/viewer-configstore`, `cmd/viewer-instancestore`, `cmd/viewer-fileservice`, `cmd/viewer-voice`.

### Core plugins (resident in `viewerd`)

- `internal/plugins/gateway/` — C4 HTTP gateway: browser `/ws` relay + static `fs.FS` serving with resolved-path/symlink containment. Hosts the plugin frontend asset pipeline (framework section 14.3): `assets.go` serves the `gateway:_:assets:push` RPC (one-shot or chunked `begin`/`file`/`commit` with intra-file `append` chunks; the asset id binds to the caller's origin plugin id; session mutation is lock-serialized and the 32 MiB per-file / 64 MiB total caps apply to accumulated bytes) into a content-addressed store at `<data>/plugin-assets/<id>/<hash>/` (latest 3 generations kept, `entry.json` sidecar, rebuilt from disk on boot), publishes the full `plugins:_:assets` mailbox map, and serves bundles same-origin at `/plugins/<id>/assets/<hash>/<file>` with immutable caching. `media.go` adds a generic same-origin H.264/WebRTC data plane: loopback `/api/media/publish` accepts Annex-B access units over WebSocket, short-lived `/api/media/ticket` grants browser access, and `/api/media/webrtc` relays one encoded track to bounded Pion peers; the hub knows stream IDs but no Browser/Page semantics. `fileraw.go` serves `GET /api/files/raw?ticket=` (framework §6.2 by-reference data plane): one small `file:_:ticket:resolve` bus RPC validates the HMAC ticket, then the file is streamed via `http.ServeContent` (Range/conditional requests built in; explicit MIME from the issuer for types sniffing gets wrong, e.g. SVG; `?download=1` adds `Content-Disposition: attachment` with a UTF-8 `filename*` so the browser saves instead of displaying inline — backing the files pane's download chrome action). `gateway:_:assets:remove` drops a plugin's assets (plugin-manager delete flow). Admin HTTP API: `POST /api/admin/restart` (graceful self-restart), `POST /api/admin/build-restart` (background release build, restart on success), and `POST /api/admin/schedule-restart` (`schedrestart.go`: runs the release build in the background first — restarting without rebuilding would reload the same old binary — and only a successful build arms a one-shot deferred restart; a watchdog then polls the bus every 5 s and fires the graceful restart path once the system is idle — `chat:_:chats:list` reports no `running_chat_ids` and `voice:_:sessions` no active relay; a failed build never arms and the state lands on `failed`. `GET /api/admin/schedule-restart` reports `none|building|armed|failed` so the frontend can stop waiting on a failed build; `DELETE /api/admin/schedule-restart` cancels a pending schedule or resets `failed` (idempotent, framework v0.44 — the in-flight build finishes but its building→armed/failed transition is a CAS, so a cancelled build never arms). The POST/GET/DELETE triple is the agent-facing HTTP surface for scheduling a restart after modifying viewer code. The state is in-memory only).
- `internal/plugins/gateway/fileupload.go` — `POST /api/files/upload?ticket=` resolves the independent upload ticket through `file:_:upload:resolve`, streams the request body into a same-directory temporary file, then publishes atomically. No-overwrite uses Linux `renameat2(RENAME_NOREPLACE)` and returns 409 on a final-stage collision; explicit overwrite uses `os.Rename`. Interrupted or failed uploads remove the temporary file and never leave a partial target.
- Gateway admin restart — release builds honor `VIEWER_REPO_ROOT` for isolated binaries and always target the running executable. `GET /` exposes `X-Viewer-Process`; Settings compares it before/after a normal restart and reloads only after the replacement responds, avoiding an old-process reload or a missed down/up window. Hand-started previews must unset inherited `INVOCATION_ID`; otherwise the standalone process would incorrectly wait for systemd to recreate it.
- `internal/plugins/terminal/` — PTY sessions, incremental UTF-8 decoding, 30 ms/128 KiB output coalescing, bounded snapshot ring, retained status replay, 30-second post-exit history, resize/write/RPC, process-group termination.
- `internal/plugins/supervisor/` — C0 process supervisor **and the plugin manager** (framework v0.39): registry loading (including disabled entries), managed external-plugin process groups, append-only logs, lifecycle state publication, per-plugin serialized start/restart/delete operations, exponential backoff, TERM-to-KILL tree shutdown. `manage.go` adds the manager RPC surface `supervisor:_:list/upsert/delete/start/stop` over `registry.json` (serialized atomic snapshots with in-memory rollback on persistence failure). Entries carry an optional launch `command` line (default `<path>/backend/run`; `--kernel-ws` is always appended — the fixed launch ABI), `name`, and `autostart` (default false: external plugins start manually from the manager pane). Failure policy: up to `BreakerMaxCrash` (3) consecutive crashes get retried with backoff, then the plugin is marked `broken` until a manual start; a run that stayed up past `BreakerWindow` (60 s) resets the counter. `delete` also calls `gateway:_:assets:remove` so the shell hot-unloads the plugin's frontend. As a backstop for delete paths that bypass the manager RPC, the supervisor runs a one-shot orphan-assets sweep 30 s after start (framework v0.55): `plugins:_:assets` entries whose id is neither in `registry.json` (disabled entries included) nor currently connected per `plugins:_:list` are removed via `assets:remove`.
- `internal/plugins/inspector/` — bus inspector: open `>` capture with self-origin rejection, bounded ring, compound filters, pause/resume/clear, stats, newest-first 800KB-budgeted cursor snapshots.
- `internal/plugins/configstore/`, `instancestore/`, `fileservice/` — C1–C3 core services: atomic JSON config, atomic per-instance state with retained tombstones, file resolve/read/hash (shared (size,mtime)→sha256 cache; `read` replies are hard-capped at the bus frame size minus 4 KiB envelope slack — an oversized encoded payload gets `too_large` instead of a frame the kernel would silently drain, which surfaced as client-side RPC timeouts) + short-lived HMAC file tickets (`file:_:ticket`/`file:_:ticket:resolve`, per-process random secret, 10-minute TTL) backing the gateway's `/api/files/raw` data plane + paginated directory listing (`file:_:list` hides dot-prefixed names unless `show_hidden` is true and always returns bounded pages — default 100, maximum 200 — with `{offset,limit,next_offset,has_more}`; streaming reads apply hidden and `dirs_only` filters before offset accounting, stat only the current page, and sort directories first case-insensitively within that page; an empty path means the user's home directory and there is no path containment — every local path is browsable/readable) + PDF page rasterization (`file:_:pdfpage {path, page, scale, trim_x?, trim_y?}` renders one page to WebP via mutool + ImageMagick; the server probes the content bounding box with `%@` and crops white margins to the requested percentage per axis — 100 = content box, 0 = full page, pathological boxes fall back to the full page; replies carry the raster's `image_width`/`image_height`), deduplicated renders, disk LRU cache at `<data>/pdf-pages/` keyed by path+size+mtime+page+dpi+trim (file names carry the pixel dimensions), 1 GiB budget) + file watching (`file:_:watch/unwatch` register (path, watcher id) with a 120 s TTL renewed by clients; parent-directory fsnotify events debounced 300 ms plus a 30 s stat sweep feed one verify pipeline that publishes `file:_:changed {path, exists, sha256?, mtime?}` only on real digest flips, event-driven checks invalidating the hash cache first). `internal/plugins/pluginrpc/` supplies inbox response helpers; `internal/plugins/storefile/` owns sibling-temp-file JSON replacement.
- `internal/plugins/fileservice/du.go` + `mutation.go` + `uploadticket.go` — `file:_:du {path}` enqueues a same-path-deduplicated background job on one worker, immediately acknowledges queued/running, reads at most 128 directory entries per batch with a 2ms yield, and publishes partial/final `{path,size,files,directories,errors,complete,done,cancelled}` snapshots through `file:_:du:progress`; `file:_:du:cancel` stops active or queued jobs. Traversal never follows directory symlinks. `file:_:mkdir` creates one validated basename and `file:_:delete` removes files/symlinks or recursively removes directories, rejecting filesystem roots and removing only a symlink itself. `file:_:list` accepts `dirs_only` for lazy tree loading. `file:_:upload:ticket {dir,name,overwrite}` validates a cross-platform basename and collision policy, then signs a two-minute ticket bound to the absolute target and overwrite flag with a secret independent from read tickets. `file:_:upload:resolve` is the gateway-only counterpart; read/upload tickets cannot be interchanged.
- `internal/agentdriver/` + `internal/acp/` + `internal/plugins/agenthermes/` — provider-neutral headless-agent bus types, bounded NDJSON JSON-RPC ACP stdio client (`ParseBlock`), and the single-instance `viewer.agent-hermes` service plugin (session pool, strict non-empty state validation for Hermes session loads with fresh-session fallback, immediate prompt ack, ordered event frames, retained catalog under `viewer.agent-hermes:_:catalog`, and — 0.3.0 — the `viewer.agent-hermes:_:background` RPC (`background.go`) reporting a session's live Hermes background terminal processes from the `<hermes-home>/processes.json` crash-recovery checkpoint with /proc PID + `host_start_time` liveness validation; the session struct carries the Hermes home of its profile (`resolveProfile`: `VIEWER_HERMES_PROFILE` env → target `profile` parameter → `default`)). ACP tool normalization retains nested `content[]` as input/output plus kind/locations so the chat UI can show command, read, edit and result details instead of a bare lifecycle id.
- `internal/codexserver/` + `internal/plugins/agentcodex/` — bounded Codex App Server JSONL stdio client and single-instance `viewer.agent-codex` (thread control, `openai-subscription` catalog via best-effort `model/list` — codex ≥0.151 returns the list under `data`; the legacy `models` key is intentionally unsupported). Command execution started/outputDelta/completed frames retain their shared item id as `activity_id`; chat merges them into one command block and replaces accumulated deltas with the completed item's authoritative `aggregatedOutput`.
- `internal/plugins/agentopencode/` — second ACP tenant, single-instance `viewer.agent-opencode`; unknown ACP update kinds retained as `other` blocks.
- `internal/plugins/chat/` — provider-agnostic Super Workspace orchestrator. `store.go` and `models.go` define the fresh Task/RoleSession/Decision schema; `task_api.go`, `task_read_api.go`, `runtime.go` and `recovery.go` own Task/Turn admission, reads, execution and recovery; `context.go` builds the layered Task context; `task_summary.go` produces rolling and final summaries; `decision.go` and `decision_marker.go` implement the flat Decision protocol and state machine; `chat_level_migration.go` implements the explicit offline settings-only upgrade. `store.go` creates the new schema and refuses incompatible Branch databases. Plugin config `plugins.viewer-chat` retains workspace metadata, agents, routing, summaries/Hindsight and context budgets. Roles and routing policies are domain rows in GORM/modernc SQLite. Every agent start/prompt/cancel and event/turn-ended exchange crosses the bus; chat has no provider-specific agent import or process. Turns persist the resolved execution target, blocks are coalesced before persistence, and queue/draft APIs are scoped to `(InputInstance, Task)`. `background.go` retains post-turn background-process holds per Role×Task session. `cite.go` resolves visible-message citations. `hindsight.go` treats the Chat-level bank as a derived index; SQLite remains authoritative.
- Chat Task/session ownership — `Chat → Tasks → Turns/RoleSessions/Messages` replaces Branch and lane models. Every Turn belongs to one Task; `(chat_id, task_id, role_id)` owns a provider session, queue and busy state. Ended Tasks are read-only and excluded from the Dock immediately, while completed final Task Summaries remain available to later Tasks. `decisions:respond` reuses the ordinary `send-message` continuation of the source Turn's Role session, not a fork.
- `internal/plugins/llm/` — global LLM forwarding layer (framework §8.11): the RPC `llm:_:complete {messages, json_mode?, timeout_seconds?, extra_body?} → {content, model}` forwards to an OpenAI-compatible endpoint so no plugin knows the model/endpoint/key; `extra_body` is merged verbatim into the outbound request body for endpoint-specific switches. Config `plugins.llm` is re-read per call (`active` = `{endpoint, key, model, timeout_seconds, extra_body?}` where `extra_body` supplies per-model default request fields merged under the caller's own fields, `profiles` = the frontend-managed library); on start it one-time-migrates the retired chat-owned keys. The optional HTTP facade is controlled by `plugins.llm.http {enabled, port, expose}` and hot-reloaded through `llm:_:http:configure`; it exposes `POST /v1/chat/completions`, `GET /v1/models`, and `GET /health`, transparently proxies OpenAI request/response bodies (including streaming), and always overrides the caller's `model` with the serving config's `model`, giving external tools the same central model switch as bus callers. Both the RPC and the facade share one ordered fallback chain — `active` first, then `profiles` top-down — guarded by a passive in-memory circuit breaker: an endpoint failing with a retryable error (transport, 404/408/429/5xx, malformed reply) is skipped for 60s, a non-retryable 4xx aborts the chain immediately, and any `plugins.llm` config edit clears the cooldowns. Callers may request a model by name (RPC `model` field, HTTP body `model`): several configs may carry the same model name (= that model's providers), the requested model's configs are tried first in list order, then the chain rolls down to the rest — an unknown or fully failing model still yields a result from the remaining configs, so callers never perceive a switch. `GET /v1/models` answers the union of the chain's models. `llm:_:test` probes one explicit endpoint config with a minimal completion and reports `{ok, latency_ms, model?, error?}` — isolated from the chain and never touching the breaker. `expose=false` binds `127.0.0.1`; `expose=true` binds `0.0.0.0` for LAN and `host.docker.internal` clients. Every completion gets an `X-Viewer-LLM-Request-ID` and a structured `llm HTTP completion` record in `viewerd.log` containing the original request body, actual upstream endpoint/body, upstream and client statuses, response body (capped at 4 MiB with `response_truncated`), error, peer, and duration; authorization keys are never logged. Listener errors remain visible through `llm:_:http:status` without preventing Viewer startup.
- `internal/plugins/voicecontrol/` — global voice control backend (framework §8.11, v0.49): merges every plugin's retained `voice-catalog:_:<plugin>` mailbox into one cross-plugin catalog and runs the continuous voice conversation — each transcribed utterance goes to the llm plugin with system rules + catalog + running summary + recent turns, and the model either answers directly (spoken `say`) or picks a catalog entry whose `channel` RPC is invoked, replying `{ok, say, effects}` (auto-appending `open_instance` for open-instance entries). Conversation state is in-memory per voice session (reset on `voice-control:_:enable` toggle): user/assistant history — assistant turns stored as canonical protocol JSON so the model keeps the `{"say","entry_id"}` envelope on later turns (framework v0.51) — with a running summary — over the 3000-rune budget the oldest turns fold into the summary via the llm plugin (never blocking the live loop on summarization failure), hard-capped at 40 turns. All voice llm calls carry `extra_body` `chat_template_kwargs.enable_thinking=false` for latency. Subscribes `chat:_:turn` for proactive announcements while enabled: completed turns are read out via chat's own `action:read-latest`, errors spoken directly, cancellations silent; announcements go out on `voice-control:_:announce`. Observability (v0.50): every exchange and state transition lands in a 100-entry in-memory interaction log (transcript, raw LLM output, picked entry/channel, effects, timings, frontend-reported phase), mirrored wholesale to the retained `voice-control:_:log` mailbox with `voice-control:_:log` / `voice-control:_:log:clear` RPCs; the system/summary prompt templates live in config-store `plugins.voice-control` (re-read per call, falling back to built-in defaults) and `voice-control:_:prompt` renders the effective templates, defaults, live session state, and the exact message list a command would send.
- `internal/plugins/voice/` — external voice-service relay: each `voice:_:start` reads `plugins.viewer-voice.service_ws/model/language` from config-store, opens one upstream WebSocket, forwards base64 bus chunks as binary frames and stop as JSON, normalizes service text messages into `voice:{rec}:event`, owns concurrent session cancellation plus the twenty-minute hard limit. `voice:_:sessions` lists in-flight relay ids (the gateway's scheduled-restart idle check polls it). The standalone form is `cmd/viewer-voice`.

- `internal/plugins/frontendlog/` — core diagnostic sink (framework v1.04): subscribes the ordinary event channel `frontend:_:log` and writes validated `{level,component,message,context,ts}` payloads through the same backend `slog` JSON stream as other daemon logs, adding `source=frontend`, browser origin and client timestamp. Malformed events become backend warnings; no RPC, retention or frontend subscription is involved.

### External plugins and tooling

- External plugins connect to the kernel `/ws` directly (`ws://<kernel-host>:<kernel-port>/ws`); kernel defaults to loopback. **The developer guide is `docs/plugin-development.md`** (manifest standard, launch ABI, SDK walkthroughs, frontend bundle contract, attach modes, debugging, checklist). `examples/pingpong/` demonstrates two Go SDK clients making RPC calls in both directions. Two attach modes (framework section 14.3): **standalone** (the operator starts `backend/run --kernel-ws <addr>` themselves — attach/detach is instant) and **supervised** (the plugin manager spawns and retries the process per its registry entry). Either way the backend pushes its built frontend bundle via `PushAssets` (Go) / `push_assets` (Python) after hello; the shell hot-loads it from the `plugins:_:assets` mailbox. Manifest display metadata (`name`/`icon`/`description`) passes through hello into `plugins:_:list` unchanged.
- `plugins/browser/` — external `viewer.browser` 0.2.0 managed-Chrome plugin: persistent per-page Chrome app windows under one server profile, random `page_id` identities, exact-page loopback MCP tools, mutually exclusive Agent/human leases, and a Browser Dock limited to Pages with active watchers. `backend/` owns Xvfb/Chrome/CDP, raw X11 window capture, FFmpeg H.264 encoding, page restoration, watchers and viewport ownership; `frontend/` owns same-origin WebRTC video, human input, navigation, and independent page_zoom/render_scale/FPS/bitrate controls. `backend/mcp_server.go` owns the config-store-backed (`plugins.viewer.browser.mcp`) loopback MCP listener with hot enable/disable/port replacement; `frontend/BrowserSettings.vue` exposes it through the unified plugin-manager settings host without restarting Chrome or streams. Closing a pane only unwatches; closing a Page is explicit. There is no MV3 extension, pairing protocol, JPEG screencast, backend selector, page enumeration, or current-page fallback. See `plugins/browser/README.md` for the media path and current feature boundary.
- `cmd/viewer-chat-migrate` — explicit offline one-way upgrade for the retired schema. `--data-dir PATH --yes` preserves only Chat/Role/routing settings, creates one open default Task per Chat, leaves an exact `chat.pre-task-first.sqlite3` backup, and refuses to run again over that backup. Normal runtime never invokes it or opens the legacy database.
- `scripts/` holds the Python black-box tooling (test-only): `smoke_*.py` suites, `mock_*.py` deterministic Agent fixtures, `migrate_*.py` data migrations. The Python SDK itself lives in `sdk/python/` (BusClient/Plugin + `push_assets`). `smoke_all.sh` orchestrates the full suite with `.venv/bin/python`. There is no Python product code.

## Frontend Structure

`frontend/src/`

- Global input sessions (framework v0.58, intent lifecycle v0.98) — `stores/inputSessions.ts` owns plugin-neutral, browser-persistent input records keyed by context id; `inputSessionState.ts` is the pure state machine for target/mode/revision, immutable send snapshots, queued-edit backup/restore, and conditional completion. A record binds text to `taskId`, optional `continueTurnId`, `dispatch`/`queued-update` mode and the queued dispatch id, so closing a pane cannot retarget delivery or turn an edit into a new dispatch. Completion clears only the unchanged snapshot on the original Task; later typing and Task switches survive. Plugins register activation-lifetime fallback send adapters; mounted panes may temporarily register runtime senders to add local optimistic UI without becoming required for delivery. `shell/WorkspaceBar.vue` renders the active session's draft/recording/processing/sending state plus open-target, graceful-stop and refine-then-send controls.
- Chat input lifecycle — `ComposerBox.vue` binds draft/role/one-shot options to the `chat:<view-id>` global input session. Draft text syncs through `chat:_:draft:get/set` as `chat_drafts` rows keyed by `(input_instance_id, task_id)`; `draftSync.ts` guards late RPCs by Task+generation+revision. Queued-edit keeps a separate ordinary-draft backup and pauses sync until cancel/completion. `inputDispatch.ts` builds pane-independent dispatch/queued-update RPCs from the durable intent and filters persisted Role picks against current Chat membership. `voice/inputSessionVoice.ts` snapshots the same intent before asynchronous voice operations.
- `main.ts` — Vue app bootstrap, Pinia install, shell mount; calls `loadPlugins()` (stage A) and `loadExternalPlugins()` (stage B).
- `utils/randomUUID.ts` — UUID generation for both secure localhost/HTTPS and non-secure LAN HTTP. Native `crypto.randomUUID()` is used when present; otherwise `getRandomValues` (or a final random fallback) produces an RFC 4122 UUID. Component setup must use this helper instead of directly calling `crypto.randomUUID()`, which otherwise leaves child components such as ComposerBox blank over LAN HTTP.
- Frontend diagnostics — `shell/frontendLog.ts` publishes best-effort structured `frontend:_:log` events over the shell's existing bus connection; failures are swallowed so remote logging cannot break the originating operation. It does not replace local `console.*`: callers such as chat's stale-role dispatch warning deliberately emit both copies.
- Shell — tiling workspace with one shared active-pane bar (title, status, plugin-registered chrome actions/controls, layout and common pane actions), sidebar and Settings. `stores/layout.ts` retains the binary pane tree and four browser-local modes: adaptive cascade (`shell/TilingLayout.vue` recursively splits each region on its long edge, keeping the first tile at one half), equal-width columns, equal-height rows, and free split-tree layout (`shell/SplitNode.vue`, manual horizontal/vertical split and resize). Algorithmic modes append new panes at the leaf end and suppress physical split controls; bar actions move the active pane content one step toward the root or leaf. `shell/PaneContainer.vue` renders titleless tiles and highlights the active tile. Above the tiling area sits an independent floating layer (`shell/FloatingLayer.vue` + `shell/FloatingPane.vue`): any pane with content can be lifted out of tiling, then dragged by its own title bar, resized from the bottom-right corner, raised on pointer-down (z-order), refreshed, docked back without displacing existing tiles (tiling modes append a fresh tile at the leaf end, filling the last tile when empty; free mode replaces the active pane), or closed. Dock clicks on an already-floating instance raise it instead of opening a tree pane. Dock entries carry no action buttons (framework v0.42; the one exception is the hover × on launcher instances — `DockInstance.clickCreates` entries whose provider implements `remove`, framework v0.73): singleton providers have no permanent entries and terminal instances do not dock; only pinned chats/files and Browser Pages with watchers are listed, while instance terminate/remove actions live in pane chrome (terminal's kill action kills the PTY and closes the pane; plain bar close only detaches the pane so the terminal keeps running with its scrollback). The expanded Dock foot shows the frontend build stamp (`__BUILD_TIME__`, injected by vite `define` at build time, rendered as local `YYYY-MM-DD HH:mm`). The Dock foot also carries a scheduled-restart indicator (framework v0.44): `shell/Dock.vue` polls `GET /api/admin/schedule-restart` every 15 s and shows a warning-colored clock icon while a deferred restart is building/armed (danger-colored alert after a failed build); clicking it opens Settings. The Dock is flat style — no shadow in either expanded or pinned mode.
- Programmatic Shell — `shell/programmatic.ts` serves `shell:<conn>:open` and `panes:list/focus/close/move` through the same instance adapters and pane helpers as human UI actions. ## Data Contracts

- Wire protocol: five frame types (hello/event/rpc/…), three-segment channels, inbox RPC conventions, retained mailbox semantics — see `docs/plugin-protocol.md` and `internal/protocol/protocol.go`.
- Channel grammar: dotted plugin-id-capable patterns with prefix/`*`/`>` matching; payload values are arbitrary JSON.
- Frontend types in `frontend/src/plugins/*/types.ts` mirror backend bus payloads; if a payload field changes, update the matching frontend type and all consumers.

## Persistence

- `--data-dir` (default `$XDG_DATA_HOME/viewer`, else `~/.local/share/viewer`): `config.json`, `instance.json`, external-plugin registry, and `viewerd.log`. The assembled server appends both structured `slog` records and standard-library plugin logs to `viewerd.log` while retaining stderr/journal output. `config.json` holds appearance, voice, Markdown, and chat/LLM router settings; Agent credentials and provider/model configuration stay in each Agent's own files.
- `chat.sqlite3` under the data directory: Super Workspace chats, roles, routing policies, messages, turns, blocks (via GORM/modernc). Legacy C1 roles/routing are imported exactly once when both DB tables are empty.
- `chat_drafts` rows are keyed by `(input_instance_id, task_id)` and remain transient UI state. Task, Turn, RoleSession, Message, Block, TurnSummary, TaskSummary, Decision, OperationReceipt and ContextBuild rows live in the Task-first SQLite schema. The deleted Loop plugin has no replacement table or compatibility RPC.
- Browser-local state: pane layout, sidebar state, pins, scroll positions, global input sessions (`viewer.inputSessions.v2`), Chat views (`viewer.chatViews.v2`) and recoverable voice text/status (`viewer.voiceContexts.v1`) in localStorage. Pane closure preserves active recording runtimes; a full page refresh necessarily stops MediaRecorder but restores the saved draft/partial transcript as editable content.

## Common Fault Locations

- Bus not connecting / registry empty: check kernel `--kernel-host`/`--kernel-port` reachability, gateway relay hello, `internal/kernel/` and `internal/broker/registry.go`.
- Plugin missing from `plugins:_:list`: check `internal/pluginapi/` assembly, plugin manifest/hello validation in `internal/protocol/`.
- Terminal output glitches: `internal/plugins/terminal/` coalescing/snapshot logic and `TerminalViewer.vue`.
- Chat dispatch fails: `internal/plugins/chat/` routing policies, agent catalog mailboxes, agent plugin logs, `chat.sqlite3`; check mock fixtures (`scripts/mock_*.py`) for deterministic reproduction.
- Task/Decision not advancing: inspect the Task Turn queue, RoleSession routing and `chat:_:decision` feed; malformed flat Decision markers remain visible with `parse_warning`, while stale/expired responses never dispatch.
- Voice not recording: `plugins.viewer-voice.service_ws/model/language` config, upstream service reachability, `voiceStore.ts` recording state.
- File listing wrong/security issues: `internal/plugins/fileservice/` path resolution (home-rooted default, no containment) and gateway static `fs.FS` containment.
- Frontend runtime errors: browser console; kernel/plugin logs under the data directory.

## Maintenance Rules

- Keep this file synchronized with code when responsibilities move or files are added/removed.
- Keep bus payloads and frontend TypeScript interfaces aligned.
- Do not hand-edit generated artifacts (`frontend/package-lock.json`, `frontend/dist/`, `web/dist/`, `frontend/node_modules/`).
- Standard checks: frontend `cd frontend && npx vue-tsc --noEmit && npm run build`; backend `gofmt -l . && go build ./... && go test ./...`; black-box `bash scripts/smoke_all.sh`.
- The app modifies served files only through explicit ticketed file-manager uploads or terminal/Agent/loop processes running real commands in the served root. Viewer-owned config/state/log files live under the configured data directory.
