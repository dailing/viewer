# Architecture

This document is the working project map for future agents. Read it before changing code so you can find the right file quickly and understand how the Go kernel, core plugins, frontend, terminal handling, file service, live update flow, and runtime configuration fit together.

Implementation is Go-first: the kernel and all core plugins live under `` (Go), the frontend under `frontend/` (Vue/TS). Python exists only as development tooling under `scripts/` (smoke tests, mocks, migrations); there is no Python product code. The authoritative design documents are `docs/plugin-framework.md` (plugin framework decisions) and `docs/plugin-protocol.md` (wire-level protocol spec); `README.md` is the Go-line build/run manual.

## Purpose

Local Live File Viewer is a private-network workspace for coordinating Codex, Hermes, and OpenCode roles while browsing and editing local files. A Go microkernel (`viewerd`) exposes a WebSocket bus, runs the core plugin set in-process, and serves the built Vue frontend on the same HTTP port. The normal frontend is a single Super Workspace shell with chats, roles, files, Git changes, terminals, Settings, and recursively split panes.

The application assumes a trusted machine and trusted LAN. Terminal, Git, file editing, and Agent processes can modify local files.

## Runtime Flow

1. `viewerd` (single static binary) starts the kernel on loopback `--kernel-host`/`--kernel-port` (defaults `127.0.0.1:8765`) and the gateway on `--host`/`--port` (default `127.0.0.1:18730`). All core plugins are assembled in-process and connect to the kernel over loopback WebSockets through the Go bus SDK — there is no second in-process transport. External plugins connect to the kernel `/ws` directly, and are language-independent.
2. The browser connects to `ws://<gateway>/ws`; the gateway plugin gives each browser connection a dedicated kernel connection whose hello reuses the browser UUID, then relays every later frame byte-for-byte. The same HTTP port serves the embedded frontend (`web/` embeds `web/dist`, built from `frontend`), with `viewerd --static` as the development override.
3. The frontend starts in `frontend/src/main.ts`: creates the Vue app and Pinia, mounts the shell, and lets the in-repo plugin loader register pane plugins (files, chat, voice, chat-manager). Panes, sidebar, drafts, and scroll positions persist browser-locally; `utils/storage.ts` migrates legacy `.dailing` keys on first access.
4. Chat flow: `ComposerBox.vue` sends the draft through the chat plugin RPC; chat publishes prompt/turn frames over the bus to the selected agent plugin; agent plugins (`viewer.agent-hermes`, `viewer.agent-codex`, `viewer.agent-opencode`) own ACP/App Server stdio subprocesses and publish ordered raw-plus-parsed event frames plus turn-ended events (carrying stop reason and, on prompt failure, the error text); chat persists turns/blocks in `chat.sqlite3` and the frontend incrementally reloads changed runs. A turn whose final stop reason is neither `end_turn` nor `cancelled` is surfaced as a persisted `error` message block (stop reason plus per-attempt error details) rendered as a red single-line row in the timeline. Events are correlated by echoed `turn_id`, never by session-to-turn mapping.
5. SIGINT/SIGTERM make the kernel broadcast close 4009 to all connections, then shut plugins down in reverse order and close PTYs, bounded by a 10-second deadline.

## Go Kernel Structure

``

- `internal/protocol/` — five wire-frame shapes, strong hello/envelope validation, UUIDv4 and manifest validation, dotted plugin-id-capable channel/pattern grammar, prefix/`*`/`>` matcher. Payload values are arbitrary JSON.
- `internal/broker/` — serialized subscription table, publish fanout, ordered retained mailbox replacement/replay, atomic subscribe handoff, bounded drop-new outbound queues (corr-tagged WARN on dropped RPC frames), protocol-error delivery, depth guard, no_route fast-fail for subscriber-less RPC requests. `registry.go` owns the retained `plugins:_:list` snapshot and lifecycle events.
- `internal/kernel/` — serves only `/ws`, hello identity, delivery time/origin stamps, oversize-frame rejection, one outbound writer plus ping/pong heartbeat per connection, close 4009 on shutdown. Core assembly and supervisor startup are deliberately outside the kernel.
- `sdk/go/busclient/` — concurrency-safe Go bus SDK shared by in-process and external Go plugins: transport isolation, hello + registry barrier, retained/live handler workers, protocol-error callbacks, inbox RPC/timeout/cancel mapping, exponential reconnect, state callbacks, panic recovery. `assets.go` adds `PushAssets(ctx, client, dir, manifest)`: uploads a built frontend bundle (`frontend.js` entry required) to the gateway, picking one-shot or chunked+append wire mode by size.
- `internal/pluginapi/` — in-process plugin contract, compile-time registry, inspector-first startup, reverse shutdown, loopback kernel-WS wiring, startup deadlines, plugin-level panic isolation.
- `cmd/viewerd/main.go` — assembled single binary: kernel + all core plugins + embedded frontend. Flags: `--host`, `--port`, `--kernel-host`, `--kernel-port`, `--data-dir`, `--static`, `--plugins`. Standalone forms: `cmd/viewer-kernel`, `cmd/viewer-gateway`, `cmd/viewer-terminal`, `cmd/viewer-supervisor`, `cmd/viewer-inspector`, `cmd/viewer-configstore`, `cmd/viewer-instancestore`, `cmd/viewer-fileservice`, `cmd/viewer-voice`.

### Core plugins (resident in `viewerd`)

- `internal/plugins/gateway/` — C4 HTTP gateway: browser `/ws` relay + static `fs.FS` serving with resolved-path/symlink containment. Hosts the plugin frontend asset pipeline (framework section 14.3): `assets.go` serves the `gateway:_:assets:push` RPC (one-shot or chunked `begin`/`file`/`commit` with intra-file `append` chunks; the asset id binds to the caller's origin plugin id) into a content-addressed store at `<data>/plugin-assets/<id>/<hash>/` (latest 3 generations kept, `entry.json` sidecar, rebuilt from disk on boot), publishes the full `plugins:_:assets` mailbox map, and serves bundles same-origin at `/plugins/<id>/assets/<hash>/<file>` with immutable caching. `gateway:_:assets:remove` drops a plugin's assets (plugin-manager delete flow). Admin HTTP API: `POST /api/admin/restart` (graceful self-restart), `POST /api/admin/build-restart` (background release build, restart on success), and `POST /api/admin/schedule-restart` (`schedrestart.go`: runs the release build in the background first — restarting without rebuilding would reload the same old binary — and only a successful build arms a one-shot deferred restart; a watchdog then polls the bus every 5 s and fires the graceful restart path once the system is idle — `chat:_:chats:list` reports no `running_chat_ids` and `voice:_:sessions` no active relay; a failed build never arms and the state lands on `failed`. `GET /api/admin/schedule-restart` reports `none|building|armed|failed` so the frontend can stop waiting on a failed build; `DELETE /api/admin/schedule-restart` cancels a pending schedule or resets `failed` (idempotent, framework v0.44 — the in-flight build finishes but its building→armed/failed transition is a CAS, so a cancelled build never arms). The POST/GET/DELETE triple is the agent-facing HTTP surface for scheduling a restart after modifying viewer code. The state is in-memory only).
- `internal/plugins/terminal/` — PTY sessions, incremental UTF-8 decoding, 30 ms/128 KiB output coalescing, bounded snapshot ring, retained status replay, 30-second post-exit history, resize/write/RPC, process-group termination.
- `internal/plugins/supervisor/` — C0 process supervisor **and the plugin manager** (framework v0.39): registry loading, managed external-plugin process groups, append-only logs, lifecycle state publication, serialized manual restart RPCs, exponential backoff, TERM-to-KILL tree shutdown. `manage.go` adds the manager RPC surface `supervisor:_:list/upsert/delete/start/stop` over `registry.json` (atomic tmp+rename persistence). Entries carry an optional launch `command` line (default `<path>/backend/run`; `--kernel-ws` is always appended — the fixed launch ABI), `name`, and `autostart` (default false: external plugins start manually from the manager pane). Failure policy: up to `BreakerMaxCrash` (3) consecutive crashes get retried with backoff, then the plugin is marked `broken` until a manual start; a run that stayed up past `BreakerWindow` (60 s) resets the counter. `delete` also calls `gateway:_:assets:remove` so the shell hot-unloads the plugin's frontend.
- `internal/plugins/inspector/` — bus inspector: open `>` capture with self-origin rejection, bounded ring, compound filters, pause/resume/clear, stats, newest-first 800KB-budgeted cursor snapshots.
- `internal/plugins/configstore/`, `instancestore/`, `fileservice/` — C1–C3 core services: atomic JSON config, atomic per-instance state with retained tombstones, file resolve/read/hash + unpaged directory listing (`file:_:list` filters hidden names, sorts directories first case-insensitively; an empty path means the user's home directory and there is no path containment — every local path is browsable/readable). `internal/plugins/pluginrpc/` supplies inbox response helpers; `internal/plugins/storefile/` owns sibling-temp-file JSON replacement.
- `internal/agentdriver/` + `internal/acp/` + `internal/plugins/agenthermes/` — provider-neutral headless-agent bus types, bounded NDJSON JSON-RPC ACP stdio client (`ParseBlock`), and the single-instance `viewer.agent-hermes` service plugin (session pool, strict non-empty state validation for Hermes session loads with fresh-session fallback, immediate prompt ack, ordered event frames, retained catalog under `viewer.agent-hermes:_:catalog`).
- `internal/codexserver/` + `internal/plugins/agentcodex/` — bounded Codex App Server JSONL stdio client and single-instance `viewer.agent-codex` (thread control, best-effort `model/list`, `openai-subscription` catalog).
- `internal/plugins/agentopencode/` — second ACP tenant, single-instance `viewer.agent-opencode`; unknown ACP update kinds retained as `other` blocks.
- `internal/plugins/chat/` — provider-agnostic Super Workspace orchestrator. Plugin config `plugins.viewer-chat` retains workspace metadata, `agents` mapping, LLM router, summaries/Hindsight, and word/byte context budgets; raw recent history is capped separately and the combined context bridge has a final UTF-8 byte cap that preserves the newest content. Roles and routing policies are domain rows in GORM/modernc `chat.sqlite3`. Every agent start/prompt/cancel and event/turn-ended exchange crosses the bus; chat has no ACP/App Server import, parser, process, or in-process agent interface. Chats/messages/turns/blocks persist under the data directory with the compound `(chat_id, occurred_at)` index on `message_blocks`. Routing policy resolution per dispatch is layered: the chat's `role_routing_policy_overrides[role_id]` (column `role_routing_policy_overrides`, edited per chat in ChatsPanel) beats the role's `routing_policy_id`, which beats the workspace `default_routing_policy_id`. The resolved candidate is persisted on the turn row (`agent`/`provider`/`model` columns, plus `dispatch_id` linking the turn back to the dispatch id its triggering user message carries as `turn_id`): the planned first candidate is recorded at resolution and replaced when failover moves to a later candidate, so the row ends on the candidate that actually ran. `chats:list` with a `chat_id` filter and `blocks:list` expose the chat's targeted turns as `turn_targets`, and the `chat:_:turn` feed announces them live (phase `target`; `completed` frames also carry the final target) — the pane's routing labels render from this execution record, and turns predating the columns render no label. Incoming event blocks are coalesced before persistence: consecutive same-kind `agent_text`/`thinking` deltas append into one open block per segment, and `tool_call` blocks carrying a `tool_call_id` (emitted by the ACP and Codex block parsers) merge lifecycle status updates into the single block opened by the initial call, republishing with the same block id so the frontend updates the row in place. A reused Hermes session that ends with `refusal` before emitting any event is treated as stale and retried once with a fresh session; visible refusals, fresh-session refusals, and other agents are never auto-retried. `chat:_:blocks:list` replies are byte-budgeted (`blocksReplyBudget`, under the kernel's 1 MiB frame limit — oversized publishes are rejected asynchronously and would otherwise strand the caller until timeout): an over-budget reply stops early with `truncated: true` + inclusive `next_after` cursor, and the frontend pages forward, deduplicating boundary blocks by id. The chat plugin logs bus protocol errors (e.g. `frame_too_large`) via the client error callback. Voice actions (framework §8.11, v0.49): chat publishes its voice entry catalog on the retained mailbox `voice-catalog:_:chat` (one `open-chat:<id>` entry per chat + fixed actions read-latest/dictate/stop/status, republished on start and every chat mutation) and executes entries behind `chat:_:voice:invoke {entry_id, instance_id}` → `{ok, say, effects}`; read-latest rewrites the newest assistant message into TTS-friendly prose via the llm plugin (fallback: strip code fences + truncate). Conversation, intent resolution and the cross-plugin catalog live in the voice-control plugin.
- `internal/plugins/llm/` — global LLM forwarding layer (framework §8.11): the RPC `llm:_:complete {messages, json_mode?, timeout_seconds?, extra_body?} → {content, model}` forwards to an OpenAI-compatible endpoint so no plugin knows the model/endpoint/key; `extra_body` is merged verbatim into the outbound request body for endpoint-specific switches. Config `plugins.llm` is re-read per call (`active` = `{endpoint, key, model, timeout_seconds}`, `profiles` = the frontend-managed library); on start it one-time-migrates the retired chat-owned keys. The optional loopback-only HTTP facade (v0.52) is controlled by `plugins.llm.http {enabled, port}` and hot-reloaded through `llm:_:http:configure`; it exposes `POST /v1/chat/completions`, `GET /v1/models`, and `GET /health` on `127.0.0.1`, transparently proxies OpenAI request/response bodies (including streaming), and always overrides the caller's `model` with `plugins.llm.active.model`, giving local external tools the same central model switch as bus callers. Listener errors remain visible through `llm:_:http:status` without preventing Viewer startup.
- `internal/plugins/voicecontrol/` — global voice control backend (framework §8.11, v0.49): merges every plugin's retained `voice-catalog:_:<plugin>` mailbox into one cross-plugin catalog and runs the continuous voice conversation — each transcribed utterance goes to the llm plugin with system rules + catalog + running summary + recent turns, and the model either answers directly (spoken `say`) or picks a catalog entry whose `channel` RPC is invoked, replying `{ok, say, effects}` (auto-appending `open_instance` for open-instance entries). Conversation state is in-memory per voice session (reset on `voice-control:_:enable` toggle): user/assistant history — assistant turns stored as canonical protocol JSON so the model keeps the `{"say","entry_id"}` envelope on later turns (framework v0.51) — with a running summary — over the 3000-rune budget the oldest turns fold into the summary via the llm plugin (never blocking the live loop on summarization failure), hard-capped at 40 turns. All voice llm calls carry `extra_body` `chat_template_kwargs.enable_thinking=false` for latency. Subscribes `chat:_:turn` for proactive announcements while enabled: completed turns are read out via chat's own `action:read-latest`, errors spoken directly, cancellations silent; announcements go out on `voice-control:_:announce`. Observability (v0.50): every exchange and state transition lands in a 100-entry in-memory interaction log (transcript, raw LLM output, picked entry/channel, effects, timings, frontend-reported phase), mirrored wholesale to the retained `voice-control:_:log` mailbox with `voice-control:_:log` / `voice-control:_:log:clear` RPCs; the system/summary prompt templates live in config-store `plugins.voice-control` (re-read per call, falling back to built-in defaults) and `voice-control:_:prompt` renders the effective templates, defaults, live session state, and the exact message list a command would send.
- `internal/plugins/voice/` — external voice-service relay: each `voice:_:start` reads `plugins.viewer-voice.service_ws/model/language` from config-store, opens one upstream WebSocket, forwards base64 bus chunks as binary frames and stop as JSON, normalizes service text messages into `voice:{rec}:event`, owns concurrent session cancellation plus the twenty-minute hard limit. `voice:_:sessions` lists in-flight relay ids (the gateway's scheduled-restart idle check polls it). The standalone form is `cmd/viewer-voice`.

### External plugins and tooling

- External plugins connect to the kernel `/ws` directly (`ws://<kernel-host>:<kernel-port>/ws`); kernel defaults to loopback. **The developer guide is `docs/plugin-development.md`** (manifest standard, launch ABI, SDK walkthroughs, frontend bundle contract, attach modes, debugging, checklist). `examples/pingpong/` demonstrates two Go SDK clients making RPC calls in both directions. Two attach modes (framework section 14.3): **standalone** (the operator starts `backend/run --kernel-ws <addr>` themselves — attach/detach is instant) and **supervised** (the plugin manager spawns and retries the process per its registry entry). Either way the backend pushes its built frontend bundle via `PushAssets` (Go) / `push_assets` (Python) after hello; the shell hot-loads it from the `plugins:_:assets` mailbox. Manifest display metadata (`name`/`icon`/`description`) passes through hello into `plugins:_:list` unchanged.
- `scripts/` holds the Python black-box tooling (test-only): `smoke_*.py` suites, `mock_*.py` deterministic Agent fixtures, `migrate_*.py` data migrations. The Python SDK itself lives in `sdk/python/` (BusClient/Plugin + `push_assets`). `smoke_all.sh` orchestrates the full suite with `.venv/bin/python`. There is no Python product code.

## Frontend Structure

`frontend/src/`

- `main.ts` — Vue app bootstrap, Pinia install, shell mount; calls `loadPlugins()` (stage A) and `loadExternalPlugins()` (stage B).
- Shell — split-pane shell with pane chrome (title bar, actions), sidebar, Settings; browser-local layout persistence; no global navbar. The workspace is a binary split tree (`stores/layout.ts` `LayoutNode`, rendered by `shell/SplitNode.vue`); above it sits an independent floating layer (`shell/FloatingLayer.vue` + `shell/FloatingPane.vue`): any pane with content can be lifted out of the tree (title-bar float button → `floatPane`), then dragged by its title bar, resized from the bottom-right corner, raised on pointer-down (z-order), refreshed, docked back into the tree (`dockFloating` via `openInstance`), or closed. Dock clicks on an already-floating instance raise it instead of opening a tree pane. Dock entries carry no action buttons (framework v0.42): singleton providers always dock, and instance terminate/remove actions live in pane chrome (terminal's kill action kills the PTY and closes the pane; plain title-bar close only detaches the pane so the terminal keeps running with its scrollback). The expanded Dock foot shows the frontend build stamp (`__BUILD_TIME__`, injected by vite `define` at build time, rendered as local `YYYY-MM-DD HH:mm`). The Dock foot also carries a scheduled-restart indicator (framework v0.44): `shell/Dock.vue` polls `GET /api/admin/schedule-restart` every 15 s and shows a warning-colored clock icon while a deferred restart is building/armed (danger-colored alert after a failed build); clicking it opens Settings. The Dock is flat style — no shadow in either expanded or pinned mode.
- Plugin loader — `shell/loader.ts`. Stage A: in-repo plugin modules at `src/plugins/*/index.ts` via `import.meta.glob`, per-plugin code-splitting. Stage B (framework sections 8.4/8.6): subscribes the `plugins:_:assets` mailbox and reconciles — new ids are `import(url)`ed from the gateway's content-addressed store, a changed content hash hot-reloads (deactivate → import new URL, no page refresh), a removed id deactivates and unregisters components/Dock provider (logical unload; open panes of its types fall back to the `PluginPaneHost` unknown-type placeholder). Import failures cool down 30 s per hash. The static import map in `index.html` pins bare `vue`/`pinia` to the stable vendor entries `src/externals/vue.ts|pinia.ts`, which share Rollup chunks with the app bundle so external plugins get the shell's exact Vue/Pinia singletons.
- `plugins/files/` — multi-instance file-preview browser (one virtual instance per pane). The Dock root entry (`files:root`) is a launcher that never opens: clicking it spawns a UUID instance pane (`DockProvider.clickCreates`). Each pane is FileBrowser (in-panel overlay directory listing with breadcrumb enter-navigation plus a leading `..` up-level row, toggled by a floating button; the initial root is the user's home directory) + FilePreview (extension-routed: image data URLs, markdown/html rendered via `utils/markdownRender.ts` / sandboxed iframe with a render/source toggle in the pane chrome, utf-8 text fallback; `too_large` and base64 binaries show plain notices). Reads go through `file:_:read` with client-chosen `max_bytes` (16 MB images, 4 MB text — the wire has no frame cap, only the service's inline default). `instanceStore.ts` keeps the instance registry + per-instance view state (dir, open file, mode, overlay) in one localStorage key; unpinned instances are pruned when no pane hosts them, pinned ones (pane-chrome pin action) survive pane close and reload.
- `plugins/chat/` — per-chat module: `ChatPane.vue` (dispatch semantics, incremental run reload, lazy per-segment markdown rendering with `renderedHtmlFor()`, bounded render window with detach/reattach), `ComposerBox.vue` (local draft state, 300 ms debounced auto-grow, voice input, explicit/automatic Role selection, send/stop), `voiceDictation.ts` (the pane-local half of the global voice loop, framework §8.11 v0.48: dictate→confirm state machine started from the retained `voice-fx:chat:<id>` mailbox with nonce dedupe, silence-based endpointing via `voice/silence.ts`, spoken prompts via `voice/speak.ts`, publishes `voice-control:_:resume` when a loop-handed dictation ends). The pane keeps only a render window of ≤300 messages resident (constant `WINDOW_MAX_MESSAGES`): overflow is evicted one 50-message page at a time — the top while streaming or catching up downward (scrollTop compensated by the removed height), the bottom while the user reads deep history — and evicted pages are transparently re-fetched from the server via the existing before/after composite cursors. Scrolling up more than 1.5 viewports from the live edge detaches the window (live frames beyond the window's upper edge stop merging; a 「跳到最新」 bar appears between thread and composer); scrolling back to the bottom trigger walks newer pages until caught up (reattach), while the jump bar and send-while-detached do a fresh newest-page load, and scroll-event echoes from load-time DOM shrinkage are suppressed so a reload never instantly re-detaches. Live message/block frames are batched into id-keyed Maps and flushed to reactive state every 100 ms (the user's own send echo flushes immediately), capping timeline rebuilds, cache write-backs and markdown re-renders during streaming. Dock status dots come from `dockStatus.ts`: the backend publishes a global `chat:_:turn` feed (phases `started`/`target`/`completed` — `target` announces the resolved routing candidate, `completed` adds `stop_reason` and the final target) and exposes `running_chat_ids` in `chats:list`; a chat with an in-flight turn shows green (`running`), a turn that completes while the chat has no open pane marks it unread — amber (`unread`) for a normal end, red (`error`) when the stop reason is a failure (anything but `end_turn`/`cancelled`). Read state is browser-local (`viewer.chatUnread.v1`, default all-read); opening a chat pane clears its unread entry and the dot disappears. Send immediately renders an optimistic user box (发送中 marker, then a settings-derived `Role → agent/provider/model` routing annotation once dispatch returns; failure marks the box 发送失败 with a dismiss button). Once the real user message lands, both routing labels render from the persisted turn records instead: the pane maintains a `turnTargets` map seeded by the `turn_targets` payload of every `chats:list`/`blocks:list` reply and updated live by `chat:_:turn` target/completed frames (cached in `chatCache.ts` with the window), the user box's `→` annotation groups the dispatch's turn targets by `dispatch_id`, and the role box header label reads its own turn's record — so labels reflect the candidate that actually executed (failover included), no longer mutate when routing settings change, and turns without a record render blank. Dispatch immediately renders one optimistic response box per role (shimmer placeholder until the turn's first live event lands). Each in-flight turn's box header carries a clickable `running` chip bound per turn (not per role): the pane seeds from the `running_turns` snapshot that `chats:list` returns when a `chat_id` filter is present, then follows the `chat:_:turn` feed, so the chip survives pane reloads and parallel send-now turns of the same role mark — and stop — independently. Clicking the chip arms a 10 s confirm window (chip switches to `Stop?`); a second click inside it sends `chat:_:stop` with the `turn_id` (backend `stopTurn` matches `activeTurn`), otherwise the chip reverts. When a target role already has a turn in flight, the dispatch no longer fails: the message is held in a per-chat+role in-memory queue (`queues`, capped at 32, over-capacity replies `queue_full`), the optimistic user box annotates queued roles with 排队中, and the queued turn starts automatically (single-role relay) when the running turn releases the role; the dispatch reply splits `started_role_ids` from `queued_role_ids`. The composer's lightning toggle sends with `parallel_dispatch`: the message bypasses the queue and starts immediately on a throwaway fresh session (unique per-turn runtime key in `runtimes`) that never resumes or overwrites the role's stored session and is dropped from the map when the turn ends. When enabled (`stores/chatSettings.ts`, default on), the thread renders one viewport of virtual space after the final message; initial loads and newly sent queries scroll to the message-end anchor rather than the absolute scroll-container end, while streaming updates never auto-scroll. Chat-manager mutations emit the frontend-local `viewer:chats-changed` event.
- `plugins/voice/` — headless plugin: `voiceStore.ts` owns per-composer recording/processing/ready state, one globally active MediaRecorder, 250 ms chunk encoding and bus delivery, cancellation cleanup, per-call `llm_refine` override; `speak.ts` (SpeechSynthesis single-slot speech queue) and `silence.ts` (AnalyserNode RMS trailing-silence watcher) back voice command mode; `VoiceInputButton.vue` binds state to a draft through `defineModel`.
- `plugins/chat-manager/` — chat list / Dock management; ChatsPanel edits per-chat settings including per-role routing policy overrides (`role_routing_policy_overrides`).
- `plugins/llm/` — the llm plugin's own settings pane (singleton Dock entry): master-detail library of model configs in config-store `plugins.llm.profiles` (`{id, name, endpoint, key, model, timeout_seconds}`, seeded once with llama-server/Ollama defaults), activating one by writing `plugins.llm.active`; the backend re-reads config per call so activation takes effect without restart. The pane also enables/disables the loopback OpenAI-compatible HTTP facade, edits its port, polls live listener/error status, and displays the base URL. `timeout_seconds` (default 60) bounds one completion and must cover queueing on local few-slot servers.
- `plugins/voice-control/` — global voice-control loop (framework §8.11, v0.48) **plus a singleton debug pane** (v0.50): plugin-scope controller with the Dock-foot headphone toggle (via the shell's generic `createDockActions` extension point) + global Ctrl+Shift+M; state machine off→command→busy/awaiting loops back to listening after each command (the phase is sent with every command RPC for the backend log); dictation hands off to the target pane over the retained `voice-fx:<plugin>:<instance>` mailbox and resumes on `voice-control:_:resume`; announcements from `voice-control:_:announce` pause the mic while speaking. `VoiceControlPane.vue` (Dock singleton, bi-mic) is the debug surface: 日志 tab live-subscribes the retained `voice-control:_:log` mailbox, Prompt tab edits the config-store templates and previews the rendered prompt, 功能目录 tab shows the merged catalog grouped by plugin.
- `plugins/plugin-manager/` — external plugin manager (singleton pane, framework section 8.9 master-detail): left list + create, right configuration (id, display name, plugin directory, launch command line overriding the default `backend/run`, enabled/autostart toggles) plus live lifecycle state from the `supervisor:_:states` mailbox and start/stop/restart/delete actions; all operations go through the `supervisor:_:list/upsert/delete/start/stop` RPCs.
- `plugins/settings/` — unified full-page Settings pane (`settings:main`, opened from the Dock gear): layout open mode (`stores/layout.ts` `openMode`), chat reading virtual space (`stores/chatSettings.ts`), Dock hover-expand delay (`stores/dockSettings.ts`), app theme management (`stores/theme.ts`), markdown theme overrides (`stores/markdownStyle.ts`), and backend restart / build-restart / scheduled build+restart (background build first, then idle-triggered) via the gateway admin API. The scheduled-restart button is a toggle reflecting the gateway state machine (mount + 5 s status polling, so agent-API-armed schedules show up too): building/armed shows a cancel action (DELETE), and a status line spells out none/building/armed/failed. All toggles are browser-local (localStorage) and apply immediately. The theme system (`viewer.themes.v1`) ships built-in Light/Dark themes; each theme is a complete set of the shell's `--color-*` variables plus a light/dark base scheme, applied as inline custom properties on `.app-shell` with the scheme mirrored to `data-theme` (driving `color-scheme` and the styles.css Markdown color fallback). Built-in themes can be edited and reset but not deleted; custom themes duplicate the active theme and can be renamed, edited, and deleted. The Dock foot also has a pin toggle (`stores/dockSettings.ts` `pinned`): pinned keeps the Dock expanded and its width takes real layout space (compressing the panes) instead of hover-overlaying them. The expanded width (pinned and hover-overlay alike) is adjustable by dragging the Dock's right edge and persists via `stores/dockSettings.ts` `width` (default 220px, clamped to 140–520px).

## Persistence

- `--data-dir` (default `$XDG_DATA_HOME/viewer`, else `~/.local/share/viewer`): `config.json`, `instance.json`, external-plugin registry, and `viewerd.log`. The assembled server appends both structured `slog` records and standard-library plugin logs to `viewerd.log` while retaining stderr/journal output. `config.json` holds appearance, voice, Markdown, and chat/LLM router settings; Agent credentials and provider/model configuration stay in each Agent's own files.
- `chat.sqlite3` under the data directory: Super Workspace chats, roles, routing policies, messages, turns, blocks (via GORM/modernc). Legacy C1 roles/routing are imported exactly once when both DB tables are empty.
- Browser-local state: pane layout, sidebar state, pins, drafts, scroll positions (non-namespaced localStorage, `.dailing` keys migrated).

## Common Fault Locations

- Bus not connecting / registry empty: check kernel `--kernel-host`/`--kernel-port` reachability, gateway relay hello, `internal/kernel/` and `internal/broker/registry.go`.
- Plugin missing from `plugins:_:list`: check `internal/pluginapi/` assembly, plugin manifest/hello validation in `internal/protocol/`.
- Terminal output glitches: `internal/plugins/terminal/` coalescing/snapshot logic and `TerminalViewer.vue`.
- Chat dispatch fails: `internal/plugins/chat/` routing policies, agent catalog mailboxes, agent plugin logs, `chat.sqlite3`; check mock fixtures (`scripts/mock_*.py`) for deterministic reproduction.
- Voice not recording: `plugins.viewer-voice.service_ws/model/language` config, upstream service reachability, `voiceStore.ts` recording state.
- File listing wrong/security issues: `internal/plugins/fileservice/` path resolution (home-rooted default, no containment) and gateway static `fs.FS` containment.
- Frontend runtime errors: browser console; kernel/plugin logs under the data directory.

## Maintenance Rules

- Keep this file synchronized with code when responsibilities move or files are added/removed.
- Keep bus payloads and frontend TypeScript interfaces aligned.
- Do not hand-edit generated artifacts (`frontend/package-lock.json`, `frontend/dist/`, `web/dist/`, `frontend/node_modules/`).
- Standard checks: frontend `cd frontend && npx vue-tsc --noEmit && npm run build`; backend `gofmt -l . && go build ./... && go test ./...`; black-box `bash scripts/smoke_all.sh`.
- The app is read-only for served files except terminal/Agent/loop processes, which can modify files because they run real commands in the served root. Viewer-owned config/state/log files live under the configured data directory.
